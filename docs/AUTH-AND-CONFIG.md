# Authentication and configuration

## Configuration sources

The app reads:

| Variable | Purpose |
|---|---|
| `FOUNDRY_PROJECT_ENDPOINT` | Preferred Foundry project endpoint |
| `AZURE_AI_PROJECT_ENDPOINT` | Accepted endpoint alias emitted by some tooling |
| `AZURE_AI_MODEL_DEPLOYMENT_NAME` | Model deployment used by the MAF agent |

`azd provision` writes environment-specific values to `.azure\`. That folder
is ignored by Git and must never be copied into a public handoff.

For a local process, use `azd ai agent run`, export the values from
`azd env get-values`, or copy `.env.example` to an ignored `.env` file.

## Authentication

The sample creates one `DefaultAzureCredential` instance and reuses it for the
Foundry client.

- Local development normally resolves Azure CLI or Azure Developer CLI
  credentials.
- A production hosted agent should resolve managed identity.
- In multi-tenant accounts, set `AZURE_TENANT_ID` in the ignored azd
  environment. This prevents `azd` from probing disabled guest tenants or
  tenants whose Conditional Access policy blocks Azure CLI token issuance.

For a production application with stricter predictability requirements,
replace `DefaultAzureCredential` with an explicit local credential during
development and `ManagedIdentityCredential` in the hosted environment. Keep
the selection centralized rather than constructing credentials per request.

## No-key policy

- The Foundry account generated by the current Bicep disables local
  authentication.
- The repository contains no model keys.
- Microsoft 365 app credentials must be supplied through Agents Toolkit
  environment configuration or a secret store, never `manifest.json`.
